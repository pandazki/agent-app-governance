# agent-app-governance：Cloudflare 版

[English](./README.md) · [回到仓库总览](../README.zh-CN.md)

这个版本把 Host 跑在 Cloudflare 上，把应用发布到部署在 Cloudflare 上的 PneumaSpace。你的 coding agent 在任意一台机器上的工作副本里改应用并提交，Host 负责检查改动，交给规则或你来批准，再发布出去，并写进应用的历史。Host 和本地版是同一份代码，跑在一个 Worker 后面的 Cloudflare Container 里。

## 和本地版的不同

- **记录在中心。** 每个应用的目录（源码、`.pneuma-framework/` 里的每个版本和历史、`.appgov/` 里 Host 的状态）是 R2 存储桶里的一个对象。每次操作先把它读出来，执行，再写回去，而且只有在这期间没人改过它时才写。容器的磁盘只是缓存：两次操作之间它可能消失，不会丢任何东西。agent 编辑的是一份工作副本；CLI 在 `submit` 时把它发过去，并在每次改动应用的操作之后让它和中心保持一致。
- **主人要登录。** 安装程序会生成一把主人密钥，只写一次，写进你机器上的一个文件。用它登录得到一个会话。你为自己的 agent 创建令牌。令牌可以创建应用、提交、查看状态和历史、取回工作副本、撤销和丢弃改动。它不能批准或拒绝改动，不能确认退过单向改动，不能收起、恢复、重新发布或清除应用，也不能创建令牌。这些拒绝发生在 Worker 里，不在 CLI 里。
- **应用页面要先登录。** Worker 在它自己的地址上提供本地版的应用页面。用主人密钥登录之前，它什么都不显示；登录有效 12 小时。它不截图，也没有数据快照。

## 开始之前

- **一个开通了 Workers Paid 的 Cloudflare 账户**，可以使用 Containers，并且 Wrangler 已经登录（在 `cloudflare/` 里运行 `npx wrangler login`）。账户要有一个 workers.dev 子域名；Host 就在那里提供服务，不用自定义域名。
- **一个部署在 Cloudflare 上的 PneumaSpace**（PneumaSpace 的 `cf/` 版本），它的地址，以及它的主人凭据文件。安装程序会以这个主人的身份登录一次，为 Host 创建一个令牌。它不会改动那个部署的 Worker、数据库结构、密钥或配额。
- **Docker** 要在运行，用来构建 linux/amd64 的 Host 镜像。在 arm64 的 Mac 上构建是在模拟下进行的；镜像只在 Cloudflare 上启动。
- **Node.js 20 或更新版本**，用来跑安装程序和 CLI。单跑 CLI 用 Node 18 就够。
- **Bun**（[bun.sh](https://bun.sh)），用来从 `local/web/` 构建应用页面。缺少构建工具时，安装程序会运行 `local/scripts/setup.sh` 装好它们。
- **需要联网。** 镜像会从 GitHub 按 `local/compose.yaml` 里固定的提交取 pneuma-framework，从 npm 取 Bun。

## 安装

在这个仓库的克隆里：

```sh
node cloudflare/scripts/install.mjs https://space.example.com \
  --space-owner ~/.pneuma-space/hosts/space.example.com/owner.json \
  --prefix appgov-host
```

它在改动任何东西之前，先检查 Node、Docker、Wrangler 的登录和 PneumaSpace 的登录，并构建应用页面。然后它创建 R2 存储桶 `<prefix>-folders`（位置提示 `wnam`），创建一个只带 `read`、`publish`、`invoke`、`manage` 和 `remove` 权限的 PneumaSpace 令牌，生成主人密钥，并部署名为 `<prefix>` 的 Worker 及其容器和应用页面。然后它把每个应用读一次，让每个应用在有人打开之前就有存好的视图（见下文），最后打印 Host 的地址和主人凭据文件的位置。仓库有改动之后，或者某一步失败之后，再跑一次即可：它会沿用之前建好的存储桶、令牌、主人密钥和容器密钥。

如果你的 Docker 跑在别的 context 下，先设好 `DOCKER_CONTEXT`（colima 的话：`DOCKER_CONTEXT=colima`）。

要让 Host 用你自己的域名而不是 workers.dev 地址，加上 `--domain host.example.com`。这个主机名所在的 zone 必须在同一个 Cloudflare 账号里；已经是别的 Worker 的自定义域名的主机名会被拒绝，绝不会被抢过来（自己带有 DNS 记录的主机名也一样）。安装程序把这个主机名作为自定义域名挂到 Worker 上（Worker 已经存在时，在部署之前挂上，这样在任何东西把你引到那里之前，域名就已经能访问），等到它能通过 HTTPS 访问（它先问这个 zone 自己的域名服务器，等它们有了这条记录，才通过这台机器的解析器去查这个主机名；解析器如果查得太早，会把"没有这个主机"保留最多 30 分钟；万一还是这样，安装程序会在部署之前停下并说明原因，过一会儿重跑即可继续），之后这个域名就是 Host 在所有地方给出的地址：安装程序的输出、主人凭据文件和 CLI 的会话文件、`token create`、`create` 和 `fetch` 写进 `centre.json` 的地址、给 agent 的起步说明、应用页面上的链接、页面写操作必须来自的 origin，以及应用在 PneumaSpace 上创建时登记的管理者地址。workers.dev 地址继续响应 API，所以还记着它的工作副本照常能用，而且每个回答都写明 Host 的地址：那里的 CLI 会说一次 Host 已经搬了，`node .appgov/appgov.mjs update`（如果是这次改动之前的 CLI，要运行两次：第一次取回新的 CLI）会把最近的 `centre.json` 改到这个域名，令牌不变。workers.dev 地址上的应用页面会把你转到域名；页面的会话 cookie 只属于一个地址，所以要在那里重新登录。不带 `--domain` 重跑会保留域名。要换到另一个域名或回到 workers.dev：在 Cloudflare 控制台里把这个主机名从 Worker 上移除（Workers、这个 Worker、Settings、Domains & Routes），删掉 `~/.appgov/hosts/<prefix>/install.json` 里的 `"domain"`，再运行一次安装程序（带上新的 `--domain`，或者不带）；还记着旧域名的工作副本需要 `update` 或新的 `centre.json`。在 PneumaSpace 上，应用登记的管理者地址是它最近一次经 Host 发布时的地址：之前创建的应用在下一次发布时换成新地址，在那之前仍是旧地址。

重跑部署了新构建之后，Durable Object 还在活动的应用会继续用之前的构建，直到它空闲下来；想让它马上换上新构建，以主人身份运行 `node cloudflare/bin/appgov.mjs container <app> stop`：它停掉这个应用的容器并重启它的 Durable Object，下一条命令就会用新构建启动 Host（`container <app>` 会显示正在用的镜像和 Worker 版本）。还在 2026-11-25 之前构建上的应用没有这个重启，只能等它空闲几分钟之后才换上。

## 打开应用页面，连接你的 AI 助手

打开 Host 的地址（安装程序最后打印的那个：`https://appgov-host.<subdomain>.workers.dev/`，或者你的 `--domain`），用主人凭据文件里的密钥登录（`owner.json` 里 `key` 的值）。还没有应用的时候，页面会显示做出第一个应用的两步。

1. **连接我的 AI 助手。** 给这个连接起个名字，比如用电脑的名字，然后按“获取代码”。页面会给出一段话，把它粘贴给在一个给应用用的空文件夹（比如 `~/apps`）里打开的 Claude Code 或 Codex：

   > 把这个文件夹连接到我的应用 Host。下面的命令会从我的 Host 取得 Host 自己的命令行工具，用一次性代码换一个令牌，存进 .appgov/（不要把它显示给任何人）。它需要联网；只有输出以 "connected" 开头的一行才算成功。然后读 AGENTS.md。在这里运行：`curl -fsSo .appgov-connect.cjs https://appgov-host.<subdomain>.workers.dev/connect && node .appgov-connect.cjs K7QM-4XPD-2R9T`

   `GET /connect` 返回一小段脚本，里面只有这个 Host 自己的 CLI 和它的地址，没有任何秘密；下载失败时，命令会带着 curl 的报错停下。脚本先删掉自己，把 CLI 写到 `.appgov/appgov.mjs`，再用它运行 `connect <code>`：CLI 在 Host 那里用代码换来一个令牌，写进 `.appgov/centre.json`（权限 0600，不会打印出来），然后写下 `token create --write` 会写的 `AGENTS.md` 和 `CLAUDE.md`（见下文）。除此之外什么也不写，除了你的 Host 也不从别处下载任何东西；连接失败时，脚本会把它替换掉的东西放回去，把它写下的东西删掉。页面会一直等到代码被用掉，然后显示这个连接。Codex 默认不让联网：用 `codex -c sandbox_workspace_write.network_access=true` 启动它，或者在它询问时允许这条命令。

   代码是 12 个字母和数字，只能用一次，10 分钟内有效；关掉面板或标签页，它就立刻作废；同一时间最多有 5 个代码在等待。只保存它的 SHA-256。输错的代码按地址计数（IPv6 地址按 /64 计）：同一个地址十分钟内错 20 次之后，这十分钟内不再接受它。没有所有地址共用的计数，否则任何人都能把它用光，挡住你自己的代码。核对计数、取走代码和生成令牌是一步完成的。换来的令牌就是普通的令牌，名字是你给连接起的名字，有效 90 天，权限和其他令牌一样，不多不少。令牌不能生成代码：代码只能在页面上、在你的会话里生成。

2. **让它做你的第一个应用。** 页面接着会给出一句可以说的话，你也可以用自己的话说想要什么。agent 会用 `node .appgov/appgov.mjs create <name>` 创建应用，然后在那里把它做出来。按 PneumaSpace 的默认配额，这个部署能放 5 个应用、3 个临时应用（每个预览算一个），同时唤醒的应用最多 2 个。

每个连接都列在首页底部的“AI 助手”下面，写着连接它的是哪个 agent、什么时候连接的、最近一次什么时候用过（精确到小时）；在终端里创建的令牌也在里面。“撤销”会说明它做什么，并请你确认；确认后令牌立刻失效，那个文件夹里的文件不受影响。“再连接一个”会生成新的代码。

## 或者在终端里给 agent 一个令牌

```sh
node cloudflare/bin/appgov.mjs --host https://appgov-host.<subdomain>.workers.dev login
node cloudflare/bin/appgov.mjs --host https://appgov-host.<subdomain>.workers.dev token create --label laptop --write ~/apps
```

（用了 `--domain` 的话，用 `--host https://host.example.com`：安装程序打印出的那个地址。）

`login` 读取主人凭据文件，把会话（12 小时）存在它旁边。`token create --write ~/apps` 把中心的地址和一个新的令牌写进 `~/apps/.appgov/centre.json`（权限 0600），不会把令牌打印出来。它还在旁边写下这个中心部署时带的 CLI（`~/apps/.appgov/appgov.mjs`），以及一个 `AGENTS.md`（Claude Code 通过 `CLAUDE.md` 读到它），告诉在 `~/apps` 里启动的 agent：这个目录是什么，怎样列出、创建和取回应用，以及 `centre.json` 是凭据，不能打印、复制或提交。你在这个 `AGENTS.md` 里、它写的那一段之外留下的文字会保留。你的 agent 在 `~/apps` 里工作。`token list` 和 `token revoke <id>` 用来管理令牌。

历史记录按中心认证的凭据写下是谁做的，而不是按 CLI 运行时所在的环境：用主人会话做的操作记为主人的；用令牌做的操作记为 CLI 识别出的 agent（识别不出就是 `unknown`），并写上令牌的标签。一次决定会写明做决定的主人，以及那是哪个 agent 的改动。

CLI 和中心会核对彼此说的 API 级别。级别不同的 CLI 会停下并说明；`node .appgov/appgov.mjs update` 会把它换成中心自己的 CLI。

## 应用页面

页面列出你的应用和等你决定的改动；这个列表来自 R2 里的摘要，不会启动任何东西。打开某个应用、某个等待的改动或回退的计划，读的是这个应用在 R2 里存好的视图；应用每次有改动，它的 Durable Object 都会写这个视图。所以打开时不启动容器，不管应用的容器在睡着，还是刚部署了新版本。不管应用存在多久，存好的视图大小都不变：它只放应用最新的 50 条历史，以及回退到离当前版本最近的 8 个版本的计划，也就是应用页面在“显示更早的”之前给出的那些。要退到更早的版本，打开时由容器算出计划（页面这时显示“正在打开…”），算好的计划会留着下次用，直到应用再有改动。历史超过这个数的应用，页面上有一个链接打开完整的历史，从应用的文件夹里读。做决定、回退和重新显示预览要经过应用的容器；打开等待的改动或回退计划时，页面会同时启动容器，这样做决定时就不用再等它启动。每个视图，以及 API 的 `status` 和 `history`，都在 `Server-Timing` 响应头里写明每次读取在 Worker 里用了多久（摘要的列表和它们的索引、存好的视图、文件夹的 etag、留着的计划，存好的东西不能用时还有容器）以及视图和计划从哪里来。过了结束时间的预览会显示为已结束。在 PneumaSpace 上被手动丢弃的预览，在你做决定之前仍会显示，决定时会说明它已经不在了。页面按浏览器的语言显示英文或中文。

你在页面上做的决定和回退，和在 CLI 里一样记为你的（`by user:owner (owner session) [owner]`），并注明是在页面上做的。输错的密钥和 `login` 计入同一个限额：同一个地址十分钟内 20 次。令牌和 CLI 的会话都打不开这个页面，来自其他网站的写入会被拒绝。页面的会话持续 12 小时；页面标题下方的“你可以在这里做决定”会打开一张卡片，上面的“退出登录”会结束它。应用和它的预览在 PneumaSpace 上打开，那里需要另外登录；页面在这些链接旁边会说明。

## 创建应用

在 `~/apps` 里：

```sh
node .appgov/appgov.mjs create todo
```

Host 会复制这个版本自己的应用模板（PneumaSpace 的 Cloudflare 起步应用，契约 `pneuma-space.cf/1`，声明了 `identity.required`），加上写给 agent 的说明，跑一遍应用的测试，把它作为预览启动一次，然后发布为 `v1`，成为 PneumaSpace 上由 `appgov` 管理的应用。工作副本放在 `~/apps/todo/`，里面有一份 CLI（`.appgov/appgov.mjs`），中心地址和令牌在 `.appgov/centre.json`。登录了那个 PneumaSpace 的人可以在 `https://<PneumaSpace 地址>/apps/todo/` 打开这个应用。

## 把应用交给 agent

用 Claude Code、Codex 或别的 agent 打开 `~/apps/todo/`，让它改。应用的 `AGENTS.md`（Claude Code 通过 `CLAUDE.md` 读到它）开头就是规则：先看 `status` 和 `history`，改文件，在 `tests/` 下加测试，跑 `npm test`，然后用 `node .appgov/appgov.mjs submit "<你要的改动>"` 提交。

要在另一台机器上继续，在那里取回一份工作副本：

```sh
APPGOV_HOST=https://appgov-host.<subdomain>.workers.dev APPGOV_TOKEN=<一个令牌> \
  node appgov.mjs fetch todo
```

落后于中心的工作副本（之后有人发布了新版本）在 `submit` 时会被拒绝；`fetch` 会把它更新到最新，但如果有会被覆盖的编辑，`fetch` 也会拒绝。在这样的副本里，`status` 会说明它落后了，以及此后中心发布了或退过了哪些版本；列为编辑的只有和副本所持版本不同的文件。`status` 和 `history` 和应用页面一样读存好的视图，所以不启动容器；历史超过 50 条的应用，`history` 通过它的容器从文件夹里读完整的历史。

`.appgov/centre.json` 里有令牌。它永远不属于任何版本，也不会随文件发出去；模板的 `.gitignore` 把它排除在 git 之外。不要把它放进任何你要分享的东西里。

## 做决定

Host 以 `personal` 模式运行。改动必须通过应用的测试（在 Host 的容器里跑；`submit` 和 `history` 会说其中有多少是应用自己的测试，改了 `app/` 却一个都没跑时会提醒），并且能在预览里启动；预览是 PneumaSpace 上的一个临时应用，用完就丢弃。常设规则放行常规改动。按这个版本的预设（`policy/personal.json`），以下改动要等你决定：应用不再声明 `identity.required`；应用不再声明一项存放数据的能力（`db`、`kv`、`files` 或 `object`；PneumaSpace 会保留数据，但应用再也读不到，所以这也是单向改动）；或者新的 SQL 删除或重命名表或列、删除索引、清空表、删除所有行。

在预览里，应用还必须按预期回答它在 `tests/preview.json` 里声明的请求；这些请求由 Host 自己发出（见"限度"）。

规则只读 SQL 文本和清单，所以一个删除或改写应用存在 `kv`、`files` 或对象里的数据的改动，在规则看来就是普通的代码改动。这种情况由 agent 自己声明：`submit --one-way "<会丢失什么>"`；应用的 `AGENTS.md` 要求它，只要改动会删除或改写已存的数据就这样做。预设定下一个改动至少要过哪一关，声明只能往上加：声明过的改动不管有哪些风险都会等你决定，你会在单独一行里读到 agent 的原话，并注明这是它自己的说法、不是规则的发现；发布之后它记为单向改动。

`submit` 回答 `needs_approval <id>` 时，agent 会停下来，把它打印的内容给你看，其中有预览的地址。在应用页面上，这个改动在“等你确认”下面：agent 用自己的话说它做了什么，是哪个 agent 用哪个令牌提交的，跑了几个应用自己的测试（或者一个都没跑），为什么要等你，回退能不能撤销它；不能的话，规则发现了什么、agent 说会失去什么，各自注明出处，以及它的预览。“让它上线”和“这次不要”就是决定；单向改动要你先勾选表示接受。一次决定和一次提交差不多久，常常 15 到 30 秒；页面会显示正在处理，并且只发送一次。如果改动是在应用后来离开了的版本上做的，它不能上线，页面会说明；你仍然可以拒绝。

在终端里，以主人身份登录后，在应用的工作副本里：

```sh
node .appgov/appgov.mjs approve <id>
node .appgov/appgov.mjs deny <id> "原因"
```

用 agent 的令牌这样做，会被 Worker 拒绝。每条命令都会先显示这个改动，再要你输入它的词（`approve` 或 `deny`）；没有交互式终端时，不管有没有登录，它都会在发出任何东西之前拒绝。

一条命令以谁的身份行事，在工作副本里外都一样：

- **以你（主人）的身份：** `approve`、`deny`、`undo --accept-one-way`、`token create`、`token revoke`、`container stop`、`take-down`、`bring-back`、`publish-again`、`clear`，以及加了 `--owner` 的 `create`、`submit`、`discard`、`undo` 或 `preview`。它们发出的是你的会话，从不是 agent 的令牌，而且只在你于交互式终端里输入命令名之后才发。历史把它们记为你的（`by owner (owner session) [owner]`）。`login` 也需要终端。
- **以 agent 的身份：** 其余所有会改变东西的命令。它们带着 `.appgov/centre.json`（或 `APPGOV_TOKEN`）里的令牌发出，记为 agent 的操作，并带上令牌的标签，即使运行它的是你。没有令牌时会被拒绝，绝不会退而使用你的会话。
- **读取**（`status`、`history`、`list`、`fetch`）不改变任何东西，也不记录。它用令牌；没有令牌时用你的会话。

编程 agent 运行命令时没有交互式终端，所以你机器上一个诚实的 agent 不会替你把你的那一步做完，尽管它以你的身份运行、读得到你的会话文件。这是和本地版一样的检查，不是一把锁；见"限度"。

## 退回

在应用的页面上，当前版本所基于的每个版本都有“回到这个版本”。页面会列出这样做撤销哪些改动、已存的数据会怎样；退过单向改动时要你确认，其中提交者自己声明为单向的，会写出它和提交者的原话。回去之后，它会说一次哪些东西还留在已存的数据里，并再说一次那些原话。在终端里：

```sh
node .appgov/appgov.mjs undo --owner "原因"          # 以你的身份退回一个版本
node .appgov/appgov.mjs undo --owner --to v2 "原因"  # 直接退回到更早的某个版本
```

每条都会要你输入 `undo`。不加 `--owner` 时，工作副本里的回退带着 `.appgov/centre.json` 里的令牌发出，记为 agent 的操作：agent 就是这样回退的。

撤销把早先版本的代码放回去。如果 PneumaSpace 上还有一个文件完全相同的发布，Host 用它的类型化操作 `rollback`；否则重新上传那些文件。存储的数据保持原样。如果被退过的版本在 `pneuma-space.json` 里声明了别的存储，或者跑了早先版本没有的 SQL，`undo` 会说明：它们写下的数据仍然存着，早先的代码可能显示不出来；如果其中有提交者声明为单向的版本，`undo` 也会打印提交者的原话。退过单向改动需要主人：登录后，在终端里运行 `undo --accept-one-way "原因"`，它会先要你输入 `undo`，说明越过这个改动意味着什么之后，再要你输入 `accept`。

## 收起、恢复或清除应用

Host 知道每个应用在不在 PneumaSpace 上。应用不在时，`status`、`list`、应用列表、应用的页面和回退页面都会先说明这一点：是你收起了它，是它在 PneumaSpace 上被收起了、不是通过 Host，是 PneumaSpace 上已经没有它了，还是 PneumaSpace 没有回应。应用被收起或不见了的时候，提交、批准等待中的改动和回退都会被拒绝，也不会有任何东西自动把它重新建出来。

这些事由你来做：登录后，在终端里，每条命令都要你输入它的命令名（`clear` 要输入应用名）。在 `~/apps` 里要写上应用名；应用名后面的话是你的理由，历史会记下来。

```sh
node .appgov/appgov.mjs take-down todo "原因"   # 收起：停止服务；这里的记录和 PneumaSpace 上存储的数据都保留
node .appgov/appgov.mjs bring-back todo         # 恢复：重新提供服务，带着 PneumaSpace 保留的数据
node .appgov/appgov.mjs publish-again todo      # 重新发布：只在 PneumaSpace 上已经没有它时可用，重新创建，没有存储的数据
node .appgov/appgov.mjs clear todo              # 清除：忘掉它；只在它不提供服务时可用
```

- **收起**用的是 PneumaSpace 的 `remove`。应用停止服务；它的记录和历史留在 R2 里，存储的数据留在 PneumaSpace 上。agent 的提交会被拒绝，并用一句话说明是你收起了它。
- **恢复**用的是平台的 `resume`：应用带着它的数据，重新提供当前发布的服务。
- **重新发布**只用于 PneumaSpace 上已经没有的应用，比如在 Host 不知情的情况下在那里被移除并彻底删除的应用。这时 `status` 和页面会说它不在 PneumaSpace 上，它存储的数据已经不在了。重新发布会用当前版本重新创建它，没有任何存储的数据。
- **清除**只对不提供服务的应用有效，所以正在服务的应用要先收起。中心会忘掉这个应用：它的文件夹、历史、各个版本、等待中的改动和它们的预览、它的摘要、存好的视图、计划，以及它在 `apps.json` 里的那一项。Host 的 PneumaSpace 令牌不能彻底删除（purge），所以应用会留在 PneumaSpace 上（已移除），带着它存储的全部数据：在 PneumaSpace 的主人到 PneumaSpace 控制台里把它彻底删除之前，它的名字、应用名额和存储空间都会一直占用。确认时、在你输入应用名之前就会说明这一点，完成之后页面会给出控制台的地址。工作副本留在原处，但不能再提交。

在应用页面上，这些操作在应用页面底部、和应用详情放在一起的“收起或清除”里；应用不在的时候，这一栏默认展开。你收起的应用单独放在应用列表下方一个折叠起来的区域里。

读取来自存好的视图和摘要，它们记的是应用上次改动时 PneumaSpace 的回答。所以 Worker 还在存储桶里存着一份 PneumaSpace 上所有应用的清单（`runtime.json`，一次调用列出全部应用）。读页面、`list` 或 `status` 时，如果发现这份清单超过五分钟，就在后台要一份新的，先用手上这份回答；页面上的“现在检查”和 `status`、`list` 的 `--check` 会当场去问。清单和存好的视图哪个新就用哪个，页面和 CLI 会说明 PneumaSpace 最近一次是什么时候确认的。这四个操作，以及每次提交、批准和回退，都在容器里当场去问 PneumaSpace。这份清单由 Worker 自己去取，为此要打开兼容性标志 `global_fetch_strictly_public`，它写在 `cloudflare/wrangler.jsonc` 里，安装程序会照着写。

| CLI 用的主人会话 | `~/.appgov/hosts/<prefix>/session.json` |
| 每个应用存储的数据和它的发布 | PneumaSpace |

## 限度

- **防范的是会犯错的 agent，不是会攻击的 agent。** 应用的测试在 Host 的容器里以第二个 unix 用户运行，这个用户读不到 Host 的文件和环境变量（PneumaSpace 令牌和 Worker 发来的密钥）。它们共享内核、网络（可以上互联网）和磁盘。没有第二层沙箱。
- 没有做的：截图、数据快照、由 Host 启动 Claude Code 或 Codex（`drive` 那条路），以及 `record` 和 `review-all` 模式。只跑过 `personal` 模式。
- 只管新应用。没有办法导入已有的应用或它的数据。
- 撤销只恢复代码；存储的数据从不放回。
- **agent 从不打开正式的应用，它的改动在预览上检查。** 正式的应用和它的预览只回应登录了 PneumaSpace 的人，而 agent 的令牌是中心的令牌，不是 PneumaSpace 的，所以 agent 得到的是 401：它从不持有 PneumaSpace 的凭据，也从不读写正式应用存储的数据。检查的办法是：应用在 `tests/preview.json` 里声明能说明它正常的请求；`submit` 时，等这次改动的预览首页有了应答，Host 自己用探测时用的那个令牌发出这些请求，所以应用通过 PneumaSpace 设置的身份请求头看到的是 PneumaSpace 的主人，但看不到这个令牌本身：PneumaSpace 在请求到达应用之前就去掉了它；万一某个回答把它带了回来，Host 在检查和展示回答之前也会把它替换掉。有一个回答不符合预期，改动就被拒绝（`preview_requests_failed`），并逐个请求告诉 agent 发了什么、得到了什么。agent 写的是这份清单，不是带着令牌运行的代码。请求只发给预览：路径出不了预览，重定向只算一个状态码、从不跟随；最多 20 个请求，请求体最多 16 KB，每个 20 秒，合计 90 秒。没有这个文件的应用，预览只说明它能启动，`history` 会写明这一点。
- **预览从空的存储开始。** 预览是 PneumaSpace 上另一个应用，声明的请求就在这份空存储上运行，所以说明不了改动在正式应用的数据上表现如何。一个删除或改写已存数据的改动等你决定时，你是根据说明来决定，而不是亲眼看到哪些已存的值会消失。
- **预览启动要占用工作区的一个唤醒名额**（PneumaSpace 默认配额下共 2 个）。名额全被占用时，PneumaSpace 会拒绝启动预览；这时如果 PneumaSpace 说这个应用自己的线上实例占着一个名额、并且归这个 Host 管，Host 会让它睡下（正式发布会替换它；如果改动随后等待决定或被拒绝，下一个访问者要等应用唤醒），然后最多等一分钟，每 5 秒问一次 PneumaSpace 名额被哪些应用占着，一有空出就再发布一次预览。它从不让别的应用睡下，不管那个应用归不归它管。一直没有名额空出时，提交被拒绝（`preview_refused`）：什么都没有发布，预览在回答之前就已丢弃，回答里写明占着名额的是哪些应用，并说明稍后再试就行，因为按默认策略，唤醒的应用没有请求 5 分钟后就会睡下。正式发布也这样等名额，但不让任何应用睡下。Host 只在 PneumaSpace 说有空名额时才再发布，前后最多发布三次：在 pandazki/pneuma-space#71 之前，PneumaSpace 把每次被拒绝的启动都算作应用的一次失败，满五次就把应用隔离。
- **预览从不运行应用的定时任务。** 预览是临时应用，PneumaSpace 不会在它上面按计划触发任务；Host 的请求也到不了 `/_pneuma-space/`，那是 PneumaSpace 投递任务的路径。任务做了什么，只有应用自己的测试能说明：测试像调用普通函数一样调用任务的代码。
- PneumaSpace 的令牌不能彻底删除（purge）应用。你清除一个应用时，或者 Host 撤下一次失败的首次发布的地址时，应用会留在 PneumaSpace 上（已移除），名字会一直被占用，直到 PneumaSpace 的主人在控制台里把它彻底删除。如果 PneumaSpace 上已经有一个同名、但不归这个 Host 管的应用，`create` 会被拒绝并说明这一点；Host 从不接管或改动这样的应用。`create` 和 `status` 会打印这个应用在 PneumaSpace 上统计请求、唤醒和睡下次数的页面地址。
- 每个应用一个容器，只在要改动应用时按需启动；读应用不需要容器，除了退到最近 8 个版本之前的计划，以及历史超过 50 条的应用的完整历史。
- **应用的文件夹随每个版本变大。** 每个版本都是应用的一份完整副本（起步应用约 85 KB），每次改动应用的操作都要整份读入、整份保存这个文件夹：在下面的离线测量里，10 个版本时 1 MB，100 个版本时 8.8 MB，500 个版本时 43 MB，在一台机器上保存分别用 0.1、0.7 和 3.5 秒。一次提交在整个检查期间都占着连接，在下面的运行里约 30 秒，其中约三分之二是 PneumaSpace 先发布预览、再发布正式版本（见下面的表）。
- 默认规则靠匹配文本找破坏性 SQL，和本地版一样。
- **在你的机器上，你的会话是一个持有即可用的凭据。** 那里的 agent 以你的系统用户运行，所以读得到 `~/.appgov/hosts/<prefix>/session.json` 和旁边的主人密钥。没有交互式终端和输入的词，CLI 不会以你的身份行事；给 agent 的说明也要求它绝不读这些文件、绝不运行这些命令。但没有什么能挡住一个自己把你的会话发给 Worker 的程序，或者在自己造出的终端里运行 CLI 的程序。要防范会攻击的 agent，就把主人密钥和会话放在 agent 不运行的地方：另一个系统账户或另一台机器。
- **对 SQL 以外的存储，Host 依靠 agent 的声明。** 规则只读 SQL 文本和清单。一个删除或改写 `kv` 条目、文件或对象的改动，除非 agent 提交时加了 `--one-way`，否则会被常设规则放行。

## 跑过什么

2026-11-25，在 macOS 上用 colima，针对一个默认配额的、部署在 Cloudflare 上的 PneumaSpace：安装（以及两次重跑）、主人登录、给 agent 的一个令牌、`create`、一个由常设规则放行的常规改动、一个去掉 `identity.required` 并等待主人决定的改动（用 agent 的令牌批准被拒绝，返回 403；主人批准后上线）、`undo`、用令牌在一个空目录里 `fetch` 并从那里提交、从过期的工作副本提交被拒绝、在容器被停掉之后的提交，以及一个故意失败的测试，用来显示测试用户能读到什么（它读不到 `/data`、Host 的主目录和 Host 的环境变量，环境里也没有 `APPGOV_` 开头的变量）。离线测试（在 `cloudflare/` 里运行 `npm run setup`、`npm run typecheck`、`bun test`）覆盖了对着假平台 API 的运行时适配器、带冲突写入的记录往返、Worker 对主人和 agent 的令牌的规则、应用页面的登录和它对其他网站的防护、页面在这个版本的真实回答上的各个视图、在空目录里用页面给出的命令连接，以及在一台机器上用 CLI 走完整个流程。2026-11-26，应用页面在部署上用无头 Chrome 跑过，用了一个自己的测试应用，和主人的两个应用放在一起：没有会话时每个路径都是登录界面、错误的密钥被拒绝、cookie 的属性、令牌、CLI 会话和来自其他网站的写入被拒绝、应用列表从摘要读出而测试应用的容器一直停着、一个由规则放行的常规改动、一个去掉 `identity.required` 的改动在页面上被拒绝、一个声明为单向的改动在页面上被放行（不管按几次按钮都只发一次请求）、在页面上退回到它之前，以及退出登录。拒绝用了 3.6 秒，放行一个改动 16 到 18 秒，回退 11 秒。

之后在部署了存好的视图以后，用同样的方式（无头 Chrome，已登录，从让浏览器打开视图到视图出现在屏幕上）重新测了这些视图，每个视图在三种状态下各测五次：测试应用的容器醒着、停着、刚重跑完安装程序。单位秒，中位数和范围；“之前”是上面那次运行里每项一个样本，那时除了应用列表，每个视图都要经过应用的容器。

| 应用列表 | 0.4 到 0.8 | 0.30（0.25 到 0.35） | 0.39（0.34 到 0.47） | 0.33（0.31 到 0.33） |

容器停着时，每次读应用列表和应用页面之后，应用的 Durable Object 都说容器仍然没有运行；每个视图的 `Server-Timing` 都写着来自存好的视图、没有容器这一步。等待的改动和退回计划会在回答之后有意启动容器。Worker 内部的时间，取自这 60 次读取的 `Server-Timing`：从 R2 读存好的视图 27 到 196 毫秒（中位数 40），读文件夹的 etag 20 到 99 毫秒（中位数 33），两者同时进行；读摘要 56 到 510 毫秒（中位数 82），是最大的一步。从跑这些测量的机器发出的请求在圣何塞（SJC）进入 Cloudflare，Worker 就在那里运行（它没有启用 Smart Placement）；存储桶在 WNAM（北美西部），所以每次读取都在同一个大洲之内。容器停着时在 CLI 上运行 `status` 和 `history`：0.71 秒（0.56 到 0.71）和 0.58 秒（0.54 到 0.68），每次之后容器都仍然停着。

实际看到的兜底。手动删掉测试应用存好的视图、容器停着时，下一次打开用了 4.2 秒（其中 3.6 秒是启动容器并算出视图），并把视图存下；再下一次 0.48 秒读到它。部署之后应用的 Durable Object 里还在运行之前的构建（没有存好的视图）时，也就是它的容器在部署期间一直运行时（保持活动的对象会保留它的 Worker 版本），应用页面和退回计划通过那个构建认得的读取分别用了 1.9 和 1.8 秒，什么也没存；`container stop` 之后对象运行新的构建，下一次打开用了 3.7 秒并存下视图，再下一次 0.44 秒。

存视图给一次写入增加的时间，单独计时（`--timing` 里的 `view`）：应用有 2 到 4 个版本时，一次常规提交增加 0.64 到 0.70 秒；有 5 到 10 个版本时，一次被拦下的提交增加 1.1 到 1.5 秒，一次批准增加 1.4 到 1.8 秒，整个写入是 18 到 31 秒。它随视图里带退回计划的版本数增长；有 10 个版本的应用，视图是 74 KB。打开改动之后再批准（它的预热在大约一秒内让容器运行起来）用了 17.8 到 18.9 秒（中位数 18.3）；容器停着时直接批准用了 18.4 到 20.8 秒（中位数 18.4）。预热把启动容器和读入记录（冷的那几次是 1.0 到 1.4 秒）从批准里拿掉了，但 PneumaSpace 发布本身的波动比这更大。

做了的节省不改变任何检查：两个探测请求同时发出，而不是一个接一个；探测之后让预览休眠这一步不再等它做完；预览在正式发布进行的同时丢弃（在这个平台上正式发布从不用预览的上传，而且提交仍然要等丢弃做完才回答）；知道应用的 id 之后，查询只读这个应用的详情，创建之后也不再马上读回一次；`npm ci --ignore-scripts` 沿用同一个容器里先前一次用同样的 `package.json`、lockfile 和 `.npmrc` 装出来的依赖，那份依赖是在任何测试跑之前留下的，测试用户碰不到。没做的：任何跳过或缩短检查的做法（测试、两个探测中的任何一个、预览）；在预览回应之前或与预览同时正式发布；测试和预览同时进行（那样没通过测试的改动也会作为预览到达 PneumaSpace）；在决定发布之前就上传正式发布的包（发出去的必须是刚好在记录之前、对照封存的草稿检查过的那份副本）。两次 PneumaSpace 发布占了 30 秒里的约 20 秒，那是平台自己的工作，这个版本不改它。`create` 之前 44 秒，之后 32 到 38 秒；`undo` 9 秒；`fetch` 1 秒。
